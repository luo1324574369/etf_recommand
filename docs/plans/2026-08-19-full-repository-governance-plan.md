# 全仓库治理与问题修复计划

## 1. 目标

针对当前 `HEAD` 的全量审查结果，完成正确性、架构、数据口径、诊断能力和工程质量治理。修复后的系统必须具备可解释、可复现、无未来数据泄漏的回测结果，并只维护一条正式策略运行链路。

## 2. 已确认决策

1. 以 `strategy.multi_factor` 作为唯一正式策略运行时，旧 `StrategyEngine` 链路先保留兼容层，迁移完成后删除。
2. 核心仓位恢复为静态 50%，首次建仓后永不调仓；市场状态只影响卫星仓位。
3. Walk-Forward 使用 Anchored Walk-Forward，并保留最终不参与选择的留出测试集。
4. 交易指标只使用 Backtrader 确认成交的 `Fill` 记录计算。
5. CSI300 归因必须使用历史成分和权重；数据缺失时显式不可用，禁止空基准静默计算。
6. 打分、IC/ICIR、因子监控、分层收益和 UI 诊断共享统一因子观察模型及预处理流程。
7. 缺失估值数据使用 `None`，从该因子的截面计算中排除，不再使用 `50.0` 伪装为中性值。
8. Portfolio 买卖必须在单一数据库事务中完成，信号写入禁止 `signal_date=None`。
9. Streamlit 只依赖 service 层；保留一个完整的因子诊断面板。
10. 全量测试可收集并通过，关键治理规则加入 CI 门禁。

## 3. 领域模型

| 模型 | 责任 | 关键约束 |
|---|---|---|
| `StrategyRuntime` | 唯一策略运行入口 | 统一参数、数据输入和结果 DTO |
| `BacktestDataset` | 管理训练、验证、测试数据边界 | 任一阶段禁止读取未来区间 |
| `FactorSnapshot` | 某交易日的全 ETF 因子截面 | 原始值、缺失状态、预处理值和方向一致 |
| `FactorObservation` | 因子值与后续收益的配对观察 | 前向收益只能在观察期结束后计算 |
| `OrderIntent` | 策略产生的下单意图 | 不得直接作为成交事实或交易指标输入 |
| `Fill` | Broker 确认的实际成交 | 价格、数量、费用、时间和订单 ID 完整 |
| `PortfolioLedger` | 交易、持仓、现金的一致账本 | 单事务更新，失败整体回滚 |
| `BenchmarkSnapshot` | 某日期的基准成分与权重 | 成分和权重必须与日期匹配 |
| `FactorDiagnosticReport` | 面板展示的诊断结果 | 数据不足必须有明确状态，不返回伪造空结果 |

## 4. 分阶段实施计划

### 阶段一：建立安全基线与测试门禁

- 固定当前基线结果，记录 `200 collected`、2 个收集错误和 8 个行为失败。
- 修复失效入口：`presentation.cli`、`presentation.app` 以及脚本中的已删除模块引用。
- 将测试按领域分组，增加最小数据库、合成行情和固定随机种子。
- 在 CI 中加入语法检查、测试收集、全量测试和关键审计脚本。

**验收：** 所有测试可收集；CI 能明确区分依赖缺失、收集错误和行为失败。

### 阶段二：修复回测数据边界与未来数据泄漏

- 重构 Backtrader 数据准备，明确 warm-up、交易区间和结束日期。
- 禁止 `start()` 或 warm-up 过程读取完整回测结束后的价格。
- 要求所有因子实现严格遵守 `end_date`，尤其是波动率、流动性和组合因子。
- 将价格历史改为按当前 bar 增量维护，或按当前日期显式切片。
- 为每个调仓日增加断言：因子输入最大日期不得晚于当前调仓日。
- 增加合成数据回归测试，验证截断历史和完整历史不会产生相同的未来因子值。

**验收：** `audit_lookahead` 通过；未来价格注入测试失败且不能被静默忽略；回测结果在数据追加未来记录后不改变历史区间结果。

### 阶段三：重建严格 OOS Walk-Forward

- 将参数搜索、验证选择和最终测试拆成明确的 `train/validation/test` 数据集。
- 参数组合只允许读取训练集；预设排序只允许使用验证集指标。
- 最终留出测试集只在预设确定后运行一次。
- 结果 DTO 增加 `evaluation_stage`、数据区间和是否参与选择的字段。
- UI 和 CLI 分别展示样本内、验证和样本外指标，禁止混用 `full_*` 字段。
- 更新优化器范围、测试断言和预设生成逻辑，消除 36/144 组合数漂移。

**验收：** 任一候选参数不会读取最终测试集；测试能通过 spy 或数据边界断言证明选择过程没有访问测试集。

### 阶段四：统一订单、成交与交易指标

- 引入 `OrderIntent` 和 `Fill`，策略下单只记录意图。
- 在 `notify_order` 中仅对已完成订单创建成交记录；拒单、取消和部分成交分别处理。
- 统一手续费、滑点、成交时间、数量和成交价字段。
- 交易明细、胜率、盈亏、持仓天数和换手率全部从 `Fill`/已闭合交易计算。
- 补充部分成交、订单失败、同日多次成交和核心仓位成交测试。

**验收：** 交易指标与 Broker 成交记录逐笔可追溯；不存在只有日志有交易、Broker 没有成交的情况。

### 阶段五：修复基准与归因

- 为 CSI300 建立按日期存储的成分、权重和行业快照接口。
- 删除“最新成分复用到历史日期”的默认行为。
- `run_attribution` 对缺失历史快照返回显式 `unavailable` 状态和原因。
- 回测入口根据用户选择传入明确基准，不再固定为 `equal_weight`。
- 增加 equal-weight 与 CSI300 两种基准的端到端归因测试。

**验收：** CSI300 归因不再产生空基准、零收益或静默降级；每个归因期间都能追溯使用的基准快照。

### 阶段六：统一因子计算与诊断

- 建立统一的 `FactorSnapshot` 构建服务，统一缺失值、Winsorize、group z-score、方向和截面范围。
- 打分、IC/ICIR、因子失效监控、分层收益全部消费同一快照。
- 删除 `build_factor_diagnostics` 中独立的普通 mean/std 口径，直接复用统一统计结果。
- 实现五组分层收益、剔除持续月份、滚动 IC/ICIR 和实际使用权重历史。
- 缺失 PE/PB/股息率保持 `None`，在截面统计中排除并在诊断中展示缺失率。
- 保留单一 `_render_factor_diagnostics_section`，移除占位输出和重复计算路径。

**验收：** UI 展示的 IC、ICIR、权重和分层收益与策略实际使用数据逐项一致；数据不足时显示状态而非空表或 0 值。

### 阶段七：收敛架构与分层边界

- 以 `multi_factor` 作为正式运行时，建立 service 层编排接口和结果 DTO。
- Streamlit 删除 Repository、数据源和数据库连接的直接依赖。
- 将数据准备、回测编排、诊断转换从 Streamlit 移入 service 层。
- 将 `multi_factor.py` 拆为因子监控、仓位管理、市场状态、订单执行和诊断组件。
- 迁移旧 `StrategyService` 的调用方、测试和脚本到新入口。
- 兼容层稳定后删除旧 `StrategyEngine`、重复因子和重复配置。

**验收：** presentation 只依赖 service；仓库中只有一套正式策略因子、配置和结果模型。

### 阶段八：账本事务与信号持久化

- 为买入、卖出和清仓封装单一事务边界。
- 交易、持仓和现金更新任一步失败则整体回滚。
- 增加余额不足、持仓不足、重复成交和并发写入校验。
- `StrategyService.run_strategy` 在生成信号前解析并校验交易日期。
- Repository 层统一使用非空类型和数据库约束。

**验收：** 故障注入测试证明账本不会出现部分提交；所有信号记录都有有效日期。

### 阶段九：文档、迁移与最终验证

- 更新 README、策略文档、回测指标说明和 CLI 使用说明。
- 标注历史结果不可与新口径直接比较的版本边界。
- 运行全量测试、数据审计、最小 Streamlit 启动检查和脚本 `--help` 检查。
- 生成一次只读的最终 OOS 报告，保存数据版本、参数、代码提交和诊断摘要。

**最终门禁：** 无收集错误、无未来数据泄漏、全量测试通过、归因状态可解释、单一策略入口生效。

## 5. 依赖与执行顺序

执行顺序必须为：阶段一 → 阶段二 → 阶段三 → 阶段四/五/六 → 阶段七/八 → 阶段九。阶段四、五、六可并行开发，但必须依赖阶段二的数据边界模型；阶段七必须等统一模型确定后进行，避免重复迁移。

## 6. 暂不做的事项

- 不在本计划内引入新的因子或优化新的投资逻辑。
- 不在数据口径稳定前比较新旧策略收益优劣。
- 不保留动态核心仓位作为隐藏兼容行为。
- 不以“测试改到通过”为目标绕过数据边界和业务约束。
