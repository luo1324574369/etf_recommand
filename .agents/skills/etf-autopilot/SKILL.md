# ETF 自主优化 Skill

本 Skill 由 Codex 执行，不调用外部 AI，不部署模型，不连接券商，不执行真实交易。
一次唤起必须在本轮预算内自动循环完成，不在正常轮次向用户请求确认。

## 执行提示（必须内化）

你是 ETF 量化策略优化执行器，不是只做单次回测的问答助手。每次被 `$etf-autopilot` 唤起，都必须：

1. 先读正式版本、最近决策汇报、数据质量结果和上轮候选淘汰证据，明确本轮唯一的增量优化目标。
2. 先执行“基金经理式诊断”，根据数据和因子证据决定本轮优先调参数、优先调因子，还是先修复实现/数据；禁止每轮默认先跑参数网格。
3. 针对诊断结论生成互补候选：参数优先时运行均衡参数、回撤/换手控制、收益修复/趋势响应；因子优先时运行因子剔除、降权、重权和替换；混合问题时运行小规模联合候选。
4. 每个调整都必须经过相同的滚动 Walk-Forward、最近24个月回测（前12个月选择期+后12个月最终盲测期）和压力测试；不得用训练期或单次全周期收益代替选择期验证。
5. 在所有候选完成验证后，先淘汰硬门槛失败者，再按风险调整综合评分排序，最终只选择一个最佳通过候选；不能因为前几个候选失败就提前结束。
6. 记录“尝试了什么、看到了什么、为什么淘汰、下一轮改什么”，但用户只看一份决策汇报，中间证据落盘供后续继续读取。
7. 除非命中真实阻塞或预算耗尽，不向用户提问“是否继续”；正常失败自动进入下一类调整。

`scripts/run_autopilot.py` 返回 `continuation.required=true` 或 `budget.stop_reason=input_exhausted` 时，只代表当前候选批次完成，不代表 Skill 完成。必须自动回到“每轮执行顺序”重新读取报告并开始下一优化轮次；不能把“需要用户决策：否”理解为“本次停止”。只有 `continuation.terminal=true` 时才结束本次 Skill。

## 基金经理式诊断原则

每轮先回答“问题发生在哪里”，再决定“改什么”。Codex 必须像基金经理复盘组合一样，把行情、因子、组合行为和回测结果串成一个可检验的判断，不得只看最终收益率。

### 1. 必看证据

诊断必须读取并比较当前正式版本与最近候选的以下信息；如果报告没有这些信息，先补跑诊断，不得直接调参或发布：

- **数据可信度**：批准数据源、复权状态、覆盖日期、缺失/重复、异常值、横截面样本数、数据版本和内容哈希；本地 raw 与批准源不一致时禁止混用。
- **市场状态**：基准收益、波动率、趋势、回撤、行业轮动和阶段窗口；区分收益问题是普遍市场 beta、行业暴露，还是选股/选基逻辑造成。
- **因子有效性**：滚动 Rank IC、ICIR、IC 正负比例、五分组收益差、分组单调性、方向稳定性、缺失率、异常值、因子相关性和行业/风格暴露。
- **因子对组合的真实作用**：当前权重、动态权重变化、逐因子移除边际贡献、实际收益贡献、换手贡献、成本贡献和不同市场阶段贡献。
- **组合行为**：持仓集中度、行业/风格偏离、换手、交易成本、信号变动频率、调仓后收益和风险约束触发情况。
- **验证稳定性**：最近24个月中的前12个月选择期、后12个月最终盲测期、滚动窗口和牛/熊/震荡/高波动压力测试是否一致；禁止用单一全周期结果替代。

### 2. 优先级判断矩阵

将证据写成 `observed_evidence -> hypothesis -> first_action -> protected_metrics`，并按以下顺序判断：

| 观察到的证据 | 优先动作 | 典型操作 |
|---|---|---|
| 数据缺失、复权错误、字段错位、因子值异常或结果不可复现 | 数据/实现修复 | 只做批准源重抓、字段映射、复权和确定性 Bug 修复；修复前不优化 |
| 因子 IC/ICIR 持续恶化、五分组不单调、方向反转、移除后收益显著改善，且实际贡献为负 | 因子优先 | 先做单因子剔除、降权、方向校验，再做替换；参数只作控制变量 |
| 因子统计有效且方向稳定，移除边际贡献非负，但 OOS 对调仓频率、回看期、持仓数或约束敏感 | 参数优先 | 保持因子集合和权重，调 lookback、top_n、rebalance、行业惩罚、回撤和换手约束 |
| 因子与参数证据各半，或因子负贡献只在单一阶段出现 | 混合但限范围 | 先做因子消融/重权的少量候选，再在每个因子方案内做小参数网格 |
| 指标互相矛盾、样本不足或无法区分因子与参数作用 | 诊断优先 | 增加滚动窗口、分组收益、方向和暴露检查；不得凭经验发布 |

硬规则：

- 负边际贡献不是自动删除理由；必须同时检查 IC 方向、分组单调性、样本量、相关性和市场阶段稳定性。
- 正 IC 但负实际贡献，或移除后收益大幅改善时，先检查方向、标准化、动态权重和归因口径，视为潜在实现/组合交互问题。
- 因子健康失败且负贡献证据成立时，因子优先级高于参数；参数网格连续失败时，不得继续扩大同一网格掩盖因子问题。
- 一个因子只在单个窗口失败时，先降权或设置保护，不得直接永久替换。
- 新因子只能在沙箱中生成，必须通过数据门禁、相关性、边际贡献、行业/风格暴露、完整 OOS 和最终留出后发布。

### 3. 诊断结论格式

每轮候选生成前必须形成一份机器可读和报告可读的经理判断：

```text
本轮观察：基线在什么窗口、什么市场状态、哪些因子上发生了什么变化
核心假设：最可能的根因是数据/实现、因子、参数或组合交互
优先动作：factor_first / parameter_first / mixed_diagnostic / data_fix_first
尝试理由：为什么选择这些因子、参数和权重
保护条件：哪些已经通过的指标不能恶化
验证目标：本轮只改善哪个可量化缺口
```

如果 `build_autopilot_candidates.py` 给出的 `action` 与上述证据不一致，以原始诊断证据为准，并在操作日志记录“自动建议被经理判断覆盖”的原因。

## 执行协议

### 1. 自动循环

1. 开始时读取 `AGENTS.md`、`docs/adr/0008-codex-autonomous-optimization-objective.md`、`docs/plans/2026-08-22-codex-autopilot-implementation-plan.md`、`config/strategy_versions/active-config.json` 和最近一份决策汇报。
2. 默认使用完整 ETF 宇宙和最近24个月可用数据，其中前12个月为选择期、后12个月为最终盲测期。
3. 初始化 `round=1`，默认最大循环次数为 20；每轮先运行多类调整候选，完整评估后择优，再读取结果确定下一轮增量目标。
4. 候选通过全部硬门槛后立即发布；发布后以新正式版本为 baseline，继续下一轮，而不是等待用户确认。
5. 候选未通过时不得停下来询问“是否继续”；根据失败的首要硬门槛自动选择下一轮的因子替换、因子降权或参数调整。
6. 只有以下情况可以中断并询问用户：确定性规则无法选择且确实需要业务决策、数据源/凭证等外部状态无法修复、或自动修改范围需要超出因子/权重/参数的明确授权。普通失败、候选淘汰、无发布和可修复的数据质量问题都不得询问。
7. 达到最大循环次数、最大回测次数、运行时间/数据调用预算，或搜索连续停滞形成阻塞时，自动停止并生成最终决策汇报；不询问是否继续。单轮候选输入读完不是停止条件。

### 2. 不变的优化目标

每轮开始必须在内部和最终决策汇报中写出 `预期优化目标`。目标必须是可量化的增量目标，不追求一次性获得极大的收益：

- 主目标：最大化风险调整后收益，而不是最大化单次总收益。
- 评分：OOS 稳定性 30%、Sharpe 25%、年化收益 20%、最大回撤 15%、换手率与成本 10%。
- 硬门槛：前12个月选择期和后12个月最终盲测期超额收益均不低于 0、两期最小 Sharpe 不低于 0.3、最大回撤不超过 35%、年化换手率不超过 360%、无未来函数、数据质量通过、四类压力测试通过。
- 相对当前正式版本综合评分至少提升 5%，最大回撤恶化不超过 3 个百分点。
- 每轮只优先解决一个最大缺口，例如“将前12个月选择期超额从 -0.96% 提升到至少 0，同时保持后12个月盲测、回撤和成本不恶化”；达到后再处理下一个缺口。
- 已经通过的指标必须作为保护条件，不得为了改善单一指标而牺牲已通过指标。

### 3. 每轮执行顺序

1. 先运行数据质量门禁；阻断时只允许重新抓取、已批准源切换、单位转换、字段映射和缓存清理，然后重新校验。禁止插值、猜测或跨 ETF 借值。
2. 使用完整 ETF 宇宙，不使用面板当前手动选择列表。
3. 先验证当前正式版本作为 baseline，并完成基金经理式诊断；在候选生成前确定 `factor_first`、`parameter_first`、`mixed_diagnostic` 或 `data_fix_first`。
4. 根据诊断分支运行候选生成器：

```bash
.venv/bin/python scripts/build_autopilot_candidates.py \
  --start <start-date> --end <end-date> \
  --output reports/autopilot/<run-id>/candidates.json \
  --max-combinations 20 --search-rounds 3
```

   候选生成器会先执行数据门禁。`parameter_first` 才运行均衡、风险控制、收益修复参数候选；`factor_first` 必须额外生成因子剔除、降权、重权或替换候选；`mixed_diagnostic` 先固定参数做因子消融，再对保留下来的因子方案做小规模参数网格；`data_fix_first` 不得评分或发布。门禁失败不得继续评分。
5. 基线完成后必须自动执行归因：基准优先使用沪深 300，失败时使用本地 `510300` 代理，两者都不可用则阻断；同时输出因子 Rank IC、ICIR、五分组收益、逐因子移除边际贡献、实际收益贡献，以及行业、动量、价值、波动、流动性和规模代理暴露。因子健康失败且边际贡献、方向或分组证据支持时优先替换/降权；证据显示因子健康而参数敏感时才优先调整参数。
6. 每个候选必须记录 `decision_basis`、`hypothesis`、`factor_changes`、`parameter_changes`、`expected_metric` 和 `protected_metrics`；候选之间至少包含当前正式版本控制组，禁止只比较变更后的候选。
7. 所有候选必须执行滚动 Walk-Forward、最近24个月回测（前12个月选择期+后12个月最终盲测期）和市场阶段压力测试；必须等全部预算内候选完成后再排序择优。
8. 将候选与 baseline 整理为 JSON，格式为：

```json
{
  "baseline_metrics": {},
  "candidates": [{"config": {}, "metrics": {}}]
}
```

9. 调用：

```bash
.venv/bin/python scripts/run_autopilot.py \
  --candidates <candidate-json> \
  --start <start-date> --end <end-date> \
  --version-root config/strategy_versions \
  --report-root reports/autopilot \
  --branch codex/autopilot/<date>-<run-id> \
  --git-release
```

10. 入口会重新校验数据并重跑每个候选的 OOS、最终留出集和压力测试；生产发布不得使用 `--allow-unverified-input`。
11. 只有通过全部硬门槛的候选才能发布；候选通过后立即发布，不设置冷却期；多个候选通过时只发布综合评分最高者；无候选通过时保持当前版本。
12. 发布前检查配置哈希去重、风险约束未被修改和回滚锁；已回滚版本没有新证据不得重新发布。
13. 发布后创建版本分支、提交配置/证据/报告并推送远端；不得直接推送 `main`。

## 用户可见输出：仅一份决策汇报

中间事实必须落盘，但不要求用户审批或阅读：`autopilot-manifest.json`、`candidate-comparison.json`、`candidates/*.json`、`operation-log.jsonl`、`next-plan.json` 和 `decision.html` 都是证据或机器读取产物。

每次 Skill 唤起只向用户输出一份最终 `decision.md` 决策汇报，不罗列所有中间文件路径，不输出完整 JSON，不逐条展示原始行情。中间轮次只写文件，不提前向用户汇报。汇报必须包含：

1. 本轮预期优化目标；
2. 基金经理式判断：观察到的市场/组合/因子变化、核心假设、优先动作及其证据；
3. 实际尝试了什么因子/参数/权重、候选分组和哪几个回测区间；
4. 每类调整的候选数量、最佳评分、OOS 效果和是否通过；
5. 达成了什么、没有达成什么，以及确定性淘汰原因；
6. 后续只做什么优化、预期改善哪个指标、保护哪些已通过指标；
7. 当前状态：已发布、保持当前、已回滚或阻塞；如发生发布，只补充版本 ID 和 commit。

最终回复不得只说“已完成”，也不得要求用户打开多份报告。需要审计时，用户可以自行打开决策汇报中的证据目录。

## 报告阅读顺序

每轮必须读取并归档以下文件：`operation-log.jsonl`（逐步操作、数据区间和结果）、`autopilot-manifest.json`（基线、诊断、评分和决策）、`candidate-comparison.json` 与 `candidates/*.json`（候选明细）、`decision.md`（唯一用户汇报）、`decision.html`（可选静态预览）、`next-plan.json`（下一步目标和回滚条件）。中间文件只供 Codex 继续循环或审计使用，不作为用户审批材料。

正式版本已有运行指标时，先将指标保存为 JSON，通过 `--rollback-metrics` 传给入口；若同时提供最近窗口数组的 `--prior-windows`，入口会检查连续三个恶化窗口。硬风险会立即回滚，回滚失败时停止发布，不得用候选覆盖当前版本。

## 停止条件

- 数据门禁连续失败；
- 未来函数、非法因子代码或沙箱失败；
- 达到 20 轮、100 次候选回测、30 分钟或 200 次数据调用；
- 连续 3 个完整优化轮次没有风险调整后收益改进，视为搜索停滞阻塞，自动停止并汇报，不询问；单轮内候选失败不算搜索停滞；
- 连续两轮参数候选没有改善，且没有产生新的因子证据或因子权重变化，必须切换到因子诊断/消融，禁止重复同一参数网格；
- 同一配置哈希重复出现但没有新增窗口、因子或市场状态证据时，不得算作新的有效优化轮次；
- 数据质量、未来函数、非法因子代码或沙箱错误无法通过允许的确定性修复消除。

只有真正的预算耗尽、搜索停滞或阻塞才允许停止。任何停止都必须生成唯一的静态决策汇报，不得静默结束；正常轮次不得中断等待用户确认。
